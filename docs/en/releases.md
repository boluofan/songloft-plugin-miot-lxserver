# Releases

Releases are tag-driven and structurally identical to `mimusic-jsplugin-audiobook` and `songloft-plugin-karaoke-lyric`: a local script bumps the version, commits, tags and pushes, and CI reacts only to `v*` tags. **Branch pushes never package or publish.**

The version is semver and matches the tag exactly (`plugin.json` holds `1.1.0`, the tag is `v1.1.0`). The host only requires three numeric segments anyway: `ValidateManifest` checks `^\d+\.\d+\.\d+`, and `checkUpdate` compares versions as plain strings with no notion of downgrade.

## Publishing once

```bash
npm run release                            # patch bump by default: 1.1.0 -> 1.1.1
npm run release -- --minor                 # 1.1.3 -> 1.2.0
npm run release -- --major                 # 1.1.3 -> 2.0.0
npm run release -- --dry-run               # print the steps only
npm run release -- --no-push               # commit and tag locally only
npm run release -- --version 1.2.0         # explicit version (republish or fill a gap)
```

`scripts/bump-version.mjs` does four things:

1. Computes the next version: takes the largest of existing tags and the manifest version, then bumps it per `--major` / `--minor` / `--patch` (default). **When the manifest version has no tag yet it ships as-is**, so the first semver release does not skip 1.1.0.
2. Writes `package.json` and `plugin.json` (`package-lock.json` is not committed in this repository, so it is neither rewritten nor staged; `npm ci` does not validate its `version` field).
3. Commits `chore(release): bump to v…` and creates an annotated tag `v…`; when the version did not actually change (first release) the commit is skipped and only the tag is created.
4. Runs `git push origin HEAD:<current branch> --follow-tags`.

A dirty work tree is refused: the package is built from the tagged commit, so uncommitted changes would silently be missing. `package-lock.json` and `src/data/*` are exempt (the former is an npm side effect, the latter is regenerated by prebuild) and only produce a warning. Being **behind the remote is refused too**: CI commits a manifest backfill to the default branch after each release, so publishing from a stale branch would be rejected at push time — the script stops before touching any file and asks for `git pull --ff-only`.

## What CI does

`.github/workflows/release-lxserver.yml` listens on `push: tags: ['v*']` and runs, in order:

1. checkout the tag;
2. verify `plugin.json.version` matches the tag and fail fast when it does not;
3. `npm ci` (including `frontend/`) and both `tsc --noEmit` passes;
4. the full plugin suite `node --experimental-strip-types --test tests/*.test.mjs` plus frontend tests;
5. `npm run build` and `npm run validate`;
6. generate the release notes and `gh release create`, uploading `dist/miot.jsplugin.zip`;
7. backfill `download_url`, `updateUrl`, `entryHash`, `zipHash` and `releaseSource` into `plugin.json` on the default branch (`lxserver`) and commit.

Step 7 only fills in what exists after publication; the version was already bumped inside the tag. `updateUrl` points at this repository's default branch, so in-app updates pull this project's package instead of falling back to upstream. `releaseSource` records the commit a package was built from and is written by CI (upstream's equivalent workflow does the same); skipping it would leave upstream's stale SHA in place.

## Release notes

Step 6 does not use GitHub's auto-generated "What's Changed". `scripts/release-notes.mjs` collects the commits between the **previous tag and the current tag** and groups them by Conventional Commits type.

```markdown
## 更新内容

### ✨ 新功能

- `voice`: 加口令 ([ccc3333](https://github.com/…/commit/ccc3333)) (commit by @boluofan)

### 🐛 修复

- `search`: 入库模式允许播放时解析外部音源 ([6e89a24](https://github.com/…/commit/6e89a24)) (commit by @hanxi)

---

**完整对比**：[v1.1.1...v1.1.2](https://github.com/…/compare/v1.1.1...v1.1.2)
```

Rules:

- Fixed section order: 💥 breaking → ✨ features → 🐛 fixes → ⚡ performance → ♻️ refactor → 📝 docs → 📦 build → 🤖 CI → ✅ tests → 🎨 style → 🔧 chore → ⏪ revert → 📌 other. Newest commit first within a section.
- Every entry ends with `(commit by @author)`: a GitHub username is extracted from noreply emails (GitHub auto-links `@username` in the notes), falling back to the commit author name for other addresses. Entries without author data omit this suffix.
- `chore(release)` is omitted: it only touches version numbers and is itself part of the batch being published.
- Unrecognised types (e.g. `wip:`) and subjects that do not match `type(scope): description` land in "other" rather than being dropped.
- "Previous tag" is the greatest semver tag **numerically lower** than the current one — not the last entry of `git tag --sort=creatordate`, which would pick a newer tag when republishing an older one and reverse the changelog range.
- The first release has no previous tag, so the range starts at the repository's first commit.
- A failing script never blocks the release: CI falls back to `--generate-notes` and still publishes the package.
- Commit subjects are therefore the only source of the notes — keep writing them as `type(scope): description`.

Preview locally (no publication, no network):

```bash
npm run release:notes -- --tag v1.1.2     # notes for v1.1.1..v1.1.2
npm run release:notes                     # omit --tag to use the tag on HEAD
```

`main` is only an upstream mirror maintained through GitHub Sync fork: it neither publishes nor receives release metadata.

## Failures and republishing

- Failing checks or build: no Release is created. Fix and republish by deleting the tag first:

  ```bash
  git tag -d v1.1.1
  git push origin :refs/tags/v1.1.1
  npm run release -- --version 1.1.1
  ```

- Release created but metadata backfill failed: re-run the workflow (Actions → Release Plugin → Re-run); it will not upload the same Release twice.
- Released versions are never reused, so a failed publication may leave a gap.

## Local validation

```bash
node --test tests/release_version.test.mjs   # version and tag rules
node --test tests/release_notes.test.mjs     # release note grouping and range
```

The first group covers patch/minor/major bumps, the first semver release not skipping a number, tags leading the manifest, the explicit error for non-semver manifests, and accepted tag shapes. The second covers section order, filtering out release commits, breaking changes on top, and range selection when republishing an older tag. Neither touches the network or publishes anything.
