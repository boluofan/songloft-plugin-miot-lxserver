# Releases

Releases are tag-driven, mirroring `mimusic-jsplugin-audiobook`: a local script bumps the version, commits, tags and pushes, and CI reacts only to `v*` tags. **Branch pushes never package, publish, or consume a revision.**

## Publishing once

```bash
npm run release                            # bump, commit, tag, push
npm run release -- --dry-run               # print the steps only
npm run release -- --no-push               # commit and tag locally only
npm run release -- --version 2026.11.23.7  # explicit version (republish or fill a gap)
```

`scripts/bump-version.mjs` does four things:

1. Computes a Beijing-time `YYYY.M.D.N` version: the first package of a day is `.0`, later ones take the largest revision across existing tags *and* the manifest version and add one; the upstream version inherited in `plugin.json` reserves its revision so a new package never collides with an already published version.
2. Writes `package.json` and `plugin.json` (`package-lock.json` is not committed in this repository, so it is neither rewritten nor staged; `npm ci` does not validate its `version` field).
3. Commits `chore(release): bump to v…` and creates an annotated tag `v…`.
4. Runs `git push origin HEAD:<current branch> --follow-tags`.

A dirty work tree is refused: the package is built from the tagged commit, so uncommitted changes would silently be missing. `package-lock.json` and `src/data/*` are exempt (the former is an npm side effect, the latter is regenerated by prebuild) and only produce a warning.

## What CI does

`.github/workflows/release.yml` listens on `push: tags: ['v*']` and runs, in order:

1. checkout the tag;
2. verify `plugin.json.version` matches the tag and fail fast when it does not;
3. `npm ci` (including `frontend/`) and both `tsc --noEmit` passes;
4. the full plugin suite `node --experimental-strip-types --test tests/*.test.mjs` plus frontend tests;
5. `npm run build` and `npm run validate`;
6. `gh release create`, uploading `dist/miot.jsplugin.zip` with GitHub-generated notes;
7. backfill `download_url`, `updateUrl`, `entryHash`, `zipHash` and `releaseSource` into `plugin.json` on the default branch (`lxserver`) and commit.

Step 7 only fills in what exists after publication; the version was already bumped inside the tag. `updateUrl` points at this repository's default branch, so in-app updates pull this project's package instead of falling back to upstream. `releaseSource` records the commit a package was built from and is written by CI (upstream's equivalent workflow does the same); skipping it would leave upstream's stale SHA in place.

`main` is only an upstream mirror maintained through GitHub Sync fork: it neither publishes nor receives release metadata.

## Failures and republishing

- Failing checks or build: no Release is created. Fix and republish by deleting the tag first:

  ```bash
  git tag -d v2026.11.23.1
  git push origin :refs/tags/v2026.11.23.1
  npm run release -- --version 2026.11.23.1
  ```

- Release created but metadata backfill failed: re-run the workflow (Actions → Release Plugin → Re-run); it will not upload the same Release twice.
- Allocated revisions are never reused, so a failed publication may leave a gap.

## Local validation

```bash
node --test tests/release_version.test.mjs   # version and tag rules
```

Those cases cover day rollover, revision increase, the legacy three-component version, and manifest-reserved revisions. They touch neither the network nor any repository.
