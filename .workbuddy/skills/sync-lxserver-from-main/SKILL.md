# 把 main 的新功能合进 lxserver

本仓库有两条长期分支，职责固定：

- **`main`**：与上游保持一致的同步分支。用户通过 GitHub 的 **Sync fork** 界面手动同步，所以 `origin/main` 就是「上游最新」。
- **`lxserver`**：个人定制分支，内置 lxserver 在线搜索源，另有若干定制（歌手名录并集、引用入库、收藏口径、在线歌手队列等）。

目标：找出 `main` 上**尚未合入 `lxserver`** 的提交，判断哪些值得合并或借鉴，按功能合过去，最后给用户一份可核对的报告。用户自己 push。

**范围边界**：只看本仓库的 `origin/main` → `lxserver`。不要找上游远程仓库、不要配 upstream remote、不要从 `songloft-org/*` 拉代码——`main` 与上游一致这件事由用户用 Sync fork 保证，skill 不需要也不应该校验。

## 阶段 0：准备

1. 定位仓库根（`git rev-parse --show-toplevel`），后续命令都在根目录执行。
2. 检查状态：`git status --porcelain`。
   - 当前分支应为 `lxserver`；不在就切过去（工作区干净才切）。
   - **允许 `package-lock.json` 脏**：本仓库既有约定不提交它。
   - 其它未提交改动 → 停下问用户要 stash 还是先提交，不要擅自丢弃。
3. 记录起始 SHA（报告要用，回滚也靠它）：`git rev-parse lxserver`。

## 阶段 1：同步本地 main

```bash
git fetch origin --prune
git rev-list --count main..origin/main      # 本地落后几个
git rev-list --count origin/main..main      # 本地是否有独有提交（正常应为 0）
```

- 落后 0 个 → 直接进下一阶段。
- 落后 >0 且本地无独有提交 → 快进：
  ```bash
  git checkout main && git merge --ff-only origin/main && git checkout lxserver
  ```
- 本地 `main` 有独有提交（`origin/main..main` 非空）→ **不要 reset、不要 --force**，报告给用户让他决定；本次分析改用 `origin/main` 作为源分支。

## 阶段 2：产出待评估清单

```bash
bash scripts/analyze_upstream.sh          # 路径相对本 skill 目录
```

脚本只读（fetch + log/show/cherry），输出：分支同步状态、定制文件清单（按 `merge-base..lxserver` 动态算，不写死）、逐条提交的 ⚠/✅/📝 标记与改动文件、汇总。

三个信息决定后面所有判断：

- **⚠ 标记**：该提交改到了 `lxserver` 有改动、`main` 没有的文件 → cherry-pick 大概率冲突，按 playbook 处理。
- **📝 标记**：改动文件**全部**是文档/日志类（`*.md`、`docs/**`、`LICENSE` 等），无代码与测试 → **纯文档提交，直接跳过**，不必再 `git show` 评估（规则见阶段 3）。
- **`git cherry` 标 `-` 的提交**：已在 `lxserver` 里以等价形式存在（patch-id 相同），**不要再 pick**。

## 阶段 3：判断取舍（三维评估）

对每条候选读实际改动再决定，不要只看 subject：

```bash
git show <sha>            # 完整 diff
git show --stat <sha>     # 只看范围
```

每条候选必须回答三个问题，**三个都答完才算评估完成**：

### Q1 适不适合合（适配性）

上游解决的那个问题，在本分支存在吗？

- 本分支**没有这个场景** → 跳过，写清理由（例：上游改的是某个仅官方客户端才走的路径）
- 本分支**已经绕开**（定制改写了同一段逻辑）→ 跳过或按 Q3 融合
- 本分支**场景不同**（定制改了接口语义、宿主契约）→ 不能直接合，只能借鉴做法
- 本分支**确实缺这个修复** → 候选通过

### Q2 是不是已经修过（重复性）

`git cherry` 只按 patch-id 判等价，**两边用不同写法修同一个 bug 时它看不出来**。必须另外查：

```bash
git log --oneline --grep='<关键词>' lxserver        # 按提交信息找同类修复
git log --oneline -S'<符号/函数名>' lxserver        # 按代码变更找
git log --oneline lxserver -- <上游改的那个文件>     # 按文件看本地都改过什么
```

再对照测试：本地是否已有覆盖同一场景的用例（测试名通常写清了 bug 形态）。判为「已修过」就进 Q3，不要直接跳过。

### Q3 谁更好（重复修复择优）

两边都修了同一个问题，**按维度比，不按感情比**：

| 维度 | 倾向采用上游 | 倾向保留本地 |
| --- | --- | --- |
| 覆盖度 | 修了边界（空值/超时/并发/重试）且有测试 | 只修主路径 |
| 与定制契合 | 改动落在通用层，不动定制挂载点 | 本地实现已经长在定制结构里 |
| 副作用面 | 改动收敛、不动公共契约 | 需要连带改多处调用方 |
| 可维护性 | 后续上游还会继续演进这块 | 本地实现更贴近本分支实际需求 |
| 契约一致性 | 与**主仓库当前实现**一致 | 与宿主契约有偏差 |

`契约一致性`这条最容易判错：本项目大量定制依赖宿主接口，**以主仓库现有实现为准**（去 `C:/dev/boluofan/songloft-org` 读对应 handler/repository）。谁和宿主现在的行为一致，谁的实现更可信。

结论只有四种，选定后写进报告：

| 结论 | 做法 |
| --- | --- |
| **A 采用上游** | `cherry-pick` 上游，**同时删除本地的等价实现**，用上游测试替换本地测试 |
| **B 保留本地** | 不 pick，报告写清「上游方案的哪个前提在本分支不成立」 |
| **C 融合**（最常见） | 取上游的算法/边界处理，装进本地结构；两份都要，但只留一套逻辑 |
| **D 都不足** | 先不合，登记到 `docs/todo.md` 等产品决策 |

**铁律**：

- 选了 A 就必须删掉本地那份，不能两份并存——否则下次同步又要重新评估一遍，而且两份实现会慢慢漂移。
- 选了 B 必须给出可验证的理由（引用行号或测试），不能只写「本地更好」。
- 无论选哪个，**pick 完必须跑测试**确认两边原本的行为都还在。

分类结论（必须写进报告）：

| 结论 | 判据 |
| --- | --- |
| **必合** | `fix` 型真实缺陷修复；与用户实际使用路径相关的 `feat` / `perf` |
| **参考优化** | 不直接 pick，但做法值得搬进定制实现（性能、边界处理、错误兜底）。报告里单列并说明借鉴点 |
| **跳过** | `chore(release)` / 版本 bump、纯 CI、依赖机器人、纯格式、**纯文档 / 排障记录**、与本插件业务无关的脚手架 |
| **需人工** | 依赖一串未合的前置提交，或改动落在定制挂载点上且看不出怎么融 |

### 纯文档 / 排障记录提交：一律跳过

本分支有自己的经验记录（`.workbuddy/memory/`、`LESSONS*.md`），**上游新增的复盘、排障日志、验证记录对定制版用户没有功能价值，还平白带来冲突合并成本**。判据是改动文件，不看 commit message 写得多像 fix：

- 改动文件**全部**是文档 / 日志类：`LESSONS.md` / `LESSONS.en.md`、`docs/**/*.md`、`README*.md`、`AGENTS*.md`、`CHANGELOG*`、`LICENSE*` 等 → **跳过，不 pick**。
- 典型形态：`docs(miot): 记录 X08E 起播失败排查` 这类只在 LESSONS 里追加一段的提交（如上游 `e67b0e8`，本地曾以 `ad44a4d` 合入——**老账不翻，新的一律跳过**）。
- **混合提交**（文档 + 少量代码 / 测试）：先看代码部分是否值得合（按 Q1/Q2/Q3）。值得合就 pick 整条，文档段落按 playbook 第 4 节处理；不值得合就整条跳过，不要为了「顺手带上文档」去 pick。
- 例外：提交虽只有文档，但**修的是本分支也引用的错误说明**（例如对外契约文档写错导致用户误配），才列为「参考优化」，手动把修正搬进本地对应文档，不 cherry-pick。

> 已合入的纯文档提交不必回滚、不必 `--amend`、不必 revert。规则只约束**本次及以后**的新候选。

三个容易误判的点：

- **发版提交一定跳过**：版本号由本分支自己的发布流程决定，合进来会和 `lxserver` 的版本推进打架。
- **不要因为「上游改了同一行」就跳过**：那正是要按 playbook 融合的地方，跳过等于永远不吸收上游。
- **注意隐式依赖**：一个 `feat` 可能依赖前面几个 `refactor`。看 `git show` 里新调用的函数是否存在，缺就按依赖顺序一起 pick。

## 阶段 4：合并

### 默认策略：逐条 cherry-pick，不整分支 merge

**不要一上来就 `git merge main`。** 整分支合并有三个问题：把发版 bump、CI、无关脚手架一次性带进来；冲突在同一个提交里一次性爆发，事后分不清是哪条改动引起的；合并后 `git cherry` 失去区分度，下次同步再也判断不出哪些是「主动选择合过的」。

按**主题**分组，同一功能的多个提交按时间顺序一起处理；组内逐个 pick，一组完成就跑一次验证。

```bash
git cherry-pick -x <sha>     # -x 必须带：提交信息里留上游来源，长期追溯靠它
```

### 什么时候才允许 merge

只有一种情况：候选提交互相依赖、`cherry-pick` 无法拆开（例：大范围重命名 + 依赖它的新功能）。这时**先在临时分支试算**，不动 `lxserver`：

```bash
git checkout -b tmp-merge-probe lxserver
git merge --no-commit --no-ff main     # 看冲突面，不提交
git diff --name-only --diff-filter=U   # 冲突文件清单
git merge --abort && git checkout lxserver && git branch -D tmp-merge-probe
```

看完冲突面再决定：冲突集中在少数几个定制文件 → 仍可回到 `cherry-pick` 逐条做；冲突横跨大量文件 → 才考虑正式 merge，并在报告里列出实际带进来的提交清单，标注哪些是「顺带进来的」。

### 冲突处理

先分类，再动手，细则见 [references/conflict-playbook.md](references/conflict-playbook.md)：

| 冲突类型 | 特征 | 策略 |
| --- | --- | --- |
| 上下文冲突 | 同一函数相邻行各改各的 | 两边都保留，按语义排好 |
| 结构冲突 | 上游改名 / 挪文件 / 换 API | 跟上游结构走，把定制逻辑移植过去 |
| 契约冲突 | 上游改了接口语义，定制依赖旧语义 | 去主仓库读当前实现，**以宿主实际行为为准** |
| 测试冲突 | 上游断言与定制行为打架 | 不许删上游断言，改成同时表达两种意图 |
| 文档冲突 | README / AGENTS 两边都加段 | 两边都要，别整段取一边 |

禁止 `-X ours` / `-X theirs` 一刀切：前者静默丢上游修复，后者静默丢定制。

冲突解决后**必做三件事**，缺一不可：

1. 跑该组相关测试（`node --test tests/<相关>.test.mjs`），不只看编译过没过。
2. `git diff` 自查：定制功能点还在不在（playbook 第 1 节清单）。
3. 搜有没有留下两份等价实现（`git log -S` 或直接搜函数名），有就删掉一份。

### 失败处理

- 一组失败且短时间解决不了 → `git cherry-pick --abort`，整组移入「需人工」，继续下一组。不要留半合并状态。
- 连续两组都卡在同一个文件 → 停下来，把这个文件的两边差异完整摆给用户看，而不是硬试。
- 候选里出现 merge commit 默认跳过（改动通常已在父提交里）；确需合并时 `git cherry-pick -x -m 1 <sha>`。

## 阶段 5：验证

```bash

```

跑 `tsc --noEmit` + 全量测试 + `songloft-plugin validate`；检测到 `frontend/` 改动时自动加跑前端两项。

## 硬约束

- **绝不 `git push`**（含 `--force`），推送永远由用户执行。
- **不在 `lxserver` 上 rebase**：该分支已推送，rebase 会改写历史。合上游只用 `cherry-pick` 或 `merge`。
- **不改写 `main`**：只允许 `--ff-only` 拉取，绝不 reset / force。
- **不删除用户定制**：定制清单见 playbook 第 1 节，合并后逐项自检。
- **不为了让测试变绿而删上游断言**：只允许改成同时表达上游预期与定制行为。
- **纯文档 / 排障记录提交不 pick**：改动全是 `*.md` / `docs/**` / LESSONS 的上游提交一律跳过；混合提交看代码部分是否值得合，不为带文档而 pick。已合入的老提交不翻账。
- 承重的产品决策（上游新功能与定制口径冲突、只能二选一）先问用户，不要自己拍。
